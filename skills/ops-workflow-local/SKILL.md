# Deliver one issue locally

Use `ops-workflow-local <issue-key>` to start or resume the selected implementation issue. The local coordinator owns tracker transitions, Git revisions, review dispatch and publication. Use the shared `ops-implement`, `ops-review-quality` and `ops-review-spec` skills. Read [the run record guide](references/run-record.md) for checkpoints and recovery. Run locally with the target repository's tools and the configured tracker and GitHub access.

## Agree on the checkout

1. Read the live issue, acceptance criteria, linked requirements and applicable parent constraints. Confirm it is an eligible implementation issue, resolve its dependencies, and verify the exact target repository and remote. A parent specification supplies context for its implementation issues. Stop for unresolved readiness, scope, access or policy decisions.
2. Follow the target repository's agent entry point and nested instructions. Read the authoritative issue-tracking, issue-scopes, issue-rules, branching, development environment, verification and review standards, including equivalent guides. Use the documented issue transitions and branch conventions. Resolve the exact starting SHA separately from the intended PR target branch, especially for stacked work. If policy or required tooling is missing, identify the blocked step and obtain a decision before taking it.
3. Check for a matching run, existing branch or registered worktree, and current tracker status. Propose the issue transition to In Progress, repository, branch name, pinned starting SHA, PR target and isolated worktree path. Include whether each existing resource would be reused. Incorporate feedback and present the revised proposal. Obtain explicit operator approval of the resulting plan before changing the issue state or creating the branch or worktree. Record the approved proposal.
4. Check that the proposed inputs still hold. Move only this issue to In Progress using the configured equivalent, then create or reuse the approved branch and worktree. Verify the repository root, remote, current branch, HEAD and worktree status. Preserve pre-existing changes. If they overlap with the task or prevent attributable verification, pause for a clean approved checkout or a decision. Use the documented repo-native setup and readiness commands. If needed, agree on minimal repeatable preparation using the repository's conventions. Record bootstrap and readiness before implementation.

## Implement and verify

- Run `ops-implement` in the prepared checkout, either directly or with an implementation agent. Pass the approved scope and criteria, repository, checkout, branch, base, readiness and limits. Include the current tested state and agreed findings in repair assignments. Collect its handoff and keep lifecycle operations with the coordinator.
- Run the required pre-review commands from the configured working directories and environment. Capture commands, actual exit status, and per-check results and evidence. A skipped, unavailable or unexecuted required check leaves the gate open. A failed required check gets a focused `ops-implement` repair and rerun when the cause is in scope. A documented policy-permitted exception needs explicit authorization for the specific result and state. Preserve the actual outcome.
- Set finite budgets before beginning, honoring repository policy. In the absence of a configured limit, allow at most two verification repair passes and two review correction passes per run, plus one recovery attempt for an incomplete reviewer result per round. Count attempts across interruptions. Pause with evidence when a budget runs out, prerequisites are unavailable, or recovery needs a scope or policy decision.
- Review the staged diff and commit only the intended changes on the approved task branch after the check gate is satisfied. Record the implementation base and exact commit SHA. Ensure verification covers that committed state. If the result was recorded against a patch, rerun on the committed revision when its equivalence cannot be established or the policy requires a rerun on the commit. Evidence must be attributable to the intended tree without unrelated changes. Keep the branch local through review and PR approval.

## Review and correct

1. Start a fresh independent reviewer for each role, `ops-review-quality` and `ops-review-spec`, through the available local agent runner. They may run in parallel or sequentially. Each reviewer must be distinct from the implementer and from the other reviewer. If separate reviewers are unavailable, pause at the review gate. Supply the same pinned implementation base and current head, current check evidence and the applicable policy. Give the spec reviewer the issue, acceptance criteria, applicable parent constraints and operator decisions. Reviewers have read-only assignments.
2. Collect both structured results before making corrections. Verify each role, provenance, base, head and coverage. The first quality review covers the full change. For each quality re-review, pass the previous quality-reviewed SHA, coverage history and prior findings. Require coverage from that SHA to the current head and rechecking of all unresolved findings. If prior coverage is invalid, follow the policy's recovery rule before accepting a result. Every spec review covers the full base-to-current-head change. Supply prior spec findings so the reviewer can record their dispositions.
3. Record both verdicts, review ranges, findings and dispositions. Keep divergent or stale results as history and obtain valid coverage for the current head. Missing results, incomplete assessments and unresolved blockers keep the gate open. Where policy permits a specific exception, record explicit operator authorization and retain the actual results, including any `fail`, `unverified` or `not assessed`.
4. Combine actionable blockers into one scoped `ops-implement` repair when practical. Record the disposition and evidence for each finding, including any evidence-based rejection. Verify again, commit the verified repair, and repeat both reviews against the new SHA. Changes to the intended revision require matching verification and both review results before proceeding.

## Approve and publish the PR

1. After the check and review gates are satisfied, present the repository, PR target, head branch and SHA, proposed title and complete body. Include the issue reference, scope, check results and limits, both role-specific verdicts and reviewed SHAs, remaining findings and dispositions, and applicable exceptions with rationale. Use the supported PR drafting helper when available. Apply operator feedback and present the updated draft for explicit approval before push or publication. An operator response can explicitly approve specified draft edits and publication together. Record the resulting approved content and exact head. A change to the head requires current checks, reviews and PR approval.
2. Reconcile GitHub state before mutation. Check for an existing PR for the source branch, and inspect the remote head and intended target. Reuse a confirmed matching PR. Reconcile any differing head, target, content, or uncertain outcome using the [recovery checks](references/run-record.md#reconcile-before-retrying). Confirm the local branch still points to the approved head. Push that exact commit to the approved branch without forcing, confirm the remote ref, and create the approved PR once. A successful push by itself leaves publication pending.
3. Verify the live PR's URL, repository, target, source, head SHA and approved content. After confirmation, move only the selected issue to In Review if the configured integration has yet to do so. Verify the tracker result. Record the URL and evidence and hand them to the operator. Human approval and merge, and any later Done transition, belong to the repository's downstream process.
